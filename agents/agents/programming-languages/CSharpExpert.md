# Desenvolvimento C# Geral

- Siga as convenções do próprio projeto em primeiro lugar, depois as convenções C# comuns.
- Mantenha naming, formatação e estrutura de projeto consistentes.

## Regras de Design de Código

- NÃO adicione interfaces/abstrações a menos que sejam usadas para dependências externas ou testes.
- Não encapsule abstrações existentes.
- Não deixe como padrão `public`. Regra de mínima exposição: `private` > `internal` > `protected` > `public`
- Mantenha nomes consistentes; escolha um estilo (ex: `WithHostPort` ou `WithBrowserPort`) e siga-o.
- Não edite código gerado automaticamente (`/api/*.cs`, `*.g.cs`, `// <auto-generated>`).
- Comentários explicam **por quê**, não o quê.
- Não adicione métodos/parâmetros não utilizados.
- Ao corrigir um método, verifique irmãos para o mesmo problema.
- Reutilize métodos existentes o máximo possível
- Adicione comentários ao adicionar métodos públicos
- Mova strings voltadas ao usuário (ex: AnalyzeAndConfirmNuGetConfigChanges) para arquivos de recurso. Mantenha texto de erro/ajuda localizável.

## Tratamento de Erros e Casos Extremos

- **Verificações de nulo**: use `ArgumentNullException.ThrowIfNull(x)`; para strings use `string.IsNullOrWhiteSpace(x)`; guarde cedo. Evite `!` genérico.
- **Exceções**: escolha tipos precisos (ex: `ArgumentException`, `InvalidOperationException`); não lance ou capture a Exception base.
- **Sem capturas silenciosas**: não engula erros; registre e relance ou deixe-os propagarem.

## Objetivos para Aplicações .NET

### Produtividade

- Prefira C# moderno (namespaces com escopo de arquivo, strings """ raw, expressões switch, ranges/índices, async streams) quando o TFM permitir.
- Mantenha diffs pequenos; reutilize código; evite novas camadas a menos que necessárias.
- Seja amigável à IDE (go-to-def, rename, quick fixes funcionam).

### Pronto para Produção

- Seguro por padrão (sem secrets; valide entrada; mínimo privilégio).
- I/O resiliente (timeouts; retry com backoff quando apropriado).
- Logging estruturado com escopos; contexto útil; sem spam de log.
- Use exceções precisas; não engula; mantenha causa/contexto.

### Performance

- Simples primeiro; otimize caminhos quentes quando medido.
- Faça stream de grandes payloads; evite alocações extras.
- Use Span/Memory/pooling quando importa.
- Async end-to-end; sem sync-over-async.

### Cloud-native / Cloud-ready

- Multiplataforma; guarde APIs específicas do SO.
- Diagnósticos: health/ready quando apropriado; métricas + rastreamentos.
- Observabilidade: ILogger + hooks OpenTelemetry.
- 12-factor: config de env; evite singletons com estado.

- Tipo de app: web / desktop / console / lib.

- **Não** defina C# mais novo que o padrão TFM.
- C# 14 (NET 10+): membros de extensão; `field` accessor; conversão `Span<T>` implícita; `?.=`; `nameof` com genérico desvinculado; lambda param mods sem tipos; construtores/eventos parciais; compound assign definido pelo usuário.

## Build

- .NET 5+: `dotnet build`, `dotnet publish`.
- .NET Framework: Pode usar `MSBuild` diretamente ou exigir Visual Studio
- Procure por targets/scripts customizados: `Directory.Build.targets`, `build.cmd/.sh`, `Build.ps1`.

## Boa Prática

- Sempre compile ou verifique docs primeiro se houver sintaxe desconhecida. Não tente corrigir a sintaxe se o código puder compilar.
- Não mude TFM, SDK ou `<LangVersion>` a menos que solicitado.

# Melhores Práticas de Programação Assíncrona

- **Naming:** todos os métodos assíncrono terminam com `Async` (incl. handlers CLI).
- **Sempre await:** sem fire-and-forget; se timeout, **cancele o trabalho**.
- **Cancelamento end-to-end:** aceite um `CancellationToken`, passe através, chame `ThrowIfCancellationRequested()` em loops, torne delays canceláveis (`Task.Delay(ms, ct)`).
- **Timeouts:** use linked `CancellationTokenSource` + `CancelAfter` (ou `WhenAny` **e** cancele a tarefa pendente).
- **Context:** use `ConfigureAwait(false)` em código helper/library; omita em entrada de app/UI.
- **Stream JSON:** `GetAsync(..., ResponseHeadersRead)` → `ReadAsStreamAsync` → `JsonDocument.ParseAsync`; evite `ReadAsStringAsync` quando grande.
- **Exit code on cancel:** retorne não-zero (ex: `130`).
- **`ValueTask`:** use apenas quando medido para ajudar; use `Task` como padrão.
- **Async dispose:** prefira `await using` para recursos assíncrono; mantenha streams/readers adequadamente proprietários.
- **Sem wrappers inúteis:** não adicione `async/await` se você só retorna a task.

- Prefira records para classes em DTOs

# Melhores práticas de testes

## Estrutura de Testes

- Projeto de testes separado: **`[NomeProjeto].Tests`**.
- Espelhe classes: `CatDoor` -> `CatDoorTests`.
- Nomeie testes por comportamento: `WhenCatMeowsThenCatDoorOpens`.
- Siga as convenções de naming existentes.
- Use **classes de instância pública**; evite campos **static**.
- Sem branching/condicionais dentro de testes.

## Testes Unitários

- Um comportamento por teste;
- Evite símbolos Unicode.
- Siga o padrão Arrange-Act-Assert (AAA)
- Use asserções claras que verifiquem o resultado expresso pelo nome do teste
- Evite múltiplas asserções em um método de teste. Neste caso, prefira múltiplos testes.
- Ao testar múltiplas pré-condições, escreva um teste para cada
- Ao testar múltiplos resultados para uma pré-condição, use testes parametrizados
- Testes devem ser capazes de rodar em qualquer ordem ou em paralelo
- Evite I/O de disco; se necessário, randomize paths, não limpe, registre localizações de arquivo.
- Teste através de **APIs públicas**; não mude visibilidade; evite `InternalsVisibleTo`.
- Exija testes para **APIs públicas** novas/alteradas.
- Affirme valores específicos e casos extremos, não resultados vagos.

## Workflow de Testes

### Executar Comando de Teste

- Procure por targets/scripts customizados: `Directory.Build.targets`, `test.ps1/.cmd/.sh`
- .NET Framework: Pode usar `vstest.console.exe` diretamente ou exigir Visual Studio Test Explorer
- Trabalhe em apenas um teste até que passe. Depois execute outros testes para garantir que nada foi quebrado.

### Cobertura de código (dotnet-coverage)

- **Ferramenta (uma vez):**
  ```
  dotnet tool install -g dotnet-coverage
  ```
- **Execute localmente (toda vez que adicionar/modificar testes):**
  ```
  dotnet-coverage collect -f cobertura -o coverage.cobertura.xml dotnet test
  ```

## Orientação Específica do Framework de Testes

- **Use o framework já na solução** (xUnit/NUnit/MSTest) para novos testes.

### xUnit

- Pacotes: `Microsoft.NET.Test.Sdk`, `xunit`, `xunit.runner.visualstudio`
- Sem atributo de classe; use `[Fact]`
- Testes parametrizados: `[Theory]` com `[InlineData]`
- Setup/teardown: construtor e `IDisposable`

### xUnit v3

- Pacotes: `xunit.v3`, `xunit.runner.visualstudio` 3.x, `Microsoft.NET.Test.Sdk`
- `ITestOutputHelper` e `[Theory]` estão em `Xunit`

### NUnit

- Pacotes: `Microsoft.NET.Test.Sdk`, `NUnit`, `NUnit3TestAdapter`
- Classe `[TestFixture]`, teste `[Test]`
- Testes parametrizados: **use `[TestCase]`**

### MSTest

- Classe `[TestClass]`, teste `[TestMethod]`
- Setup/teardown: `[TestInitialize]`, `[TestCleanup]`
- Testes parametrizados: **use `[TestMethod]` + `[DataRow]`**

### Asserções

- Se **FluentAssertions/AwesomeAssertions** já estão sendo usadas, prefira-as.
- Caso contrário, use as asserções do framework.
- Use `Throws/ThrowsAsync` (ou MSTest `Assert.ThrowsException`) para exceções.

## Mocking

- Evite mocks/Fakes se possível
- Dependências externas podem ser mockadas. Nunca mocke código cuja implementação faz parte da solução sob teste.
- Tente verificar que as saídas (ex: valores de retorno, exceções) do mock correspondem às saídas da dependência. Você pode escrever um teste para isto mas deixe marcado como skipped/explicit para que desenvolvedores possam verificar depois.
